es_token scratch-KV reservation: budget-sized carving -- 2026-08-23
====================================================================
H100 NVL, Qwen3-1.7B bf16, 112 matched decoder linears. Follow-up to
es_token_rail_op.txt / es_token_noise.txt, which left pack_width as the only
remaining lever (decode was 82% of the step, capped at 4-8 concurrent slots).

PROBLEM
-------
_np_prefill_packed carves a private KV region off the TOP of vLLM's block pool,
one disjoint slice per packed slot, because the decode driver bypasses vLLM's
scheduler and must own static KV for a captured CUDA graph. It sized each slice
at the FULL max_model_len:
    blocks_per_prompt = ceil(max_model_len / block_size) = ceil(40960/16) = 2560
against num_gpu_blocks = 395,472/16 = 24,717  ->  max 9 slots.
A 1024-token generation from a ~90-token prompt needs ~70 blocks, so this
over-reserved ~20x and was what capped pack_width at 8.

FIX
---
Reserve for the ACTUAL budget: longest prompt in the wave + max_tokens (capped at
max_model_len). _np_prefill_packed gains max_new_tokens=None (None = old
behaviour, so the NP trainer is untouched); es_token passes max_tokens.
ES_KV_FULL_RESERVE=1 restores the old carving for A/B.

SAFETY: the attention block table is zero-filled and only the first
len(block_ids) entries are written, so a slot that outgrew its slice would read
block 0 and silently corrupt ANOTHER slot's KV rather than crash. A second
assert now guarantees longest_prompt + max_new_tokens <= blocks_per_prompt *
block_size, which makes that unreachable.

  block_size=16  num_gpu_blocks=24717  max_model_len=40960
  reservation basis        blocks/slot   max slots
  max_model_len (old)         2560           9
  1024 prompt + 1024 resp      128         193
  1024 + 3072 resp             256          96

CORRECTNESS
-----------
check_kv_output_neutral.sh (separate processes per setting -- flipping the
reservation INSIDE one process reuses the CUDA graph already captured for that
bucket and makes the comparison vacuous):
  pack_width=4  tokens identical=True  payload max|diff|=0.000e+00  PASS
  pack_width=8  tokens identical=True  payload max|diff|=0.000e+00  PASS
  (sigma=0.01, T=256 -- the reservation change is byte-neutral)

check_kv_reservation.py, pack_width 4/8/16/32/64, T=256:
  [C] every slot reaches max_tokens ............ PASS at all widths
  [B] neighbour-independence .................... PASS at all widths
      (slots 0-3 fixed, all OTHER slots' CONTENT swapped -> byte-identical
       output; this is the direct test for slices aliasing each other)
check_es_parity.py: sigma=0 == stock greedy, graphed == eager BIT-FOR-BIT
  (payload max|diff| 0.000e+00), staggered-EOS bit-for-bit. ALL PASS.

FINDING: packed decode vs stock greedy is NOT bit-equal at large batch, and
that is expected, not corruption. Evidence:
  - a slot's output is independent of what the other slots contain (test [B]),
    so slices do not alias;
  - it changes with the wave WIDTH alone (slots 0-3 identical at width 4 and 16,
    different at width 32);
  - it appears at the shipping pack_width=4 too, for prompts where the top-2
    logits are close, and there the reservation change is provably byte-neutral;
  - divergence is prompt-dependent (bad slots come in pairs i, i+8 = the same
    prompt text) and compounds with generation length.
The hand-driven packed forward batches differently from vLLM's scheduler, so bf16
rounding differs and greedy argmax flips on near-ties. Comparing packed output to
stock therefore measures rounding, not KV safety -- which is why the gate checks
[A]/[B]/[C] instead.
