es_token direct-Rademacher noise fill -- 2026-08-22
====================================================
H100 NVL, Qwen3-1.7B bf16, 112 matched decoder linears, d_total = 917,504.
Follow-up to es_token_rail_op.txt, which left the per-token noise draw as the
largest remaining fixed decode cost (0.199 ms/token-step).

PROBLEM
-------
draw_noise(method="bernoulli") produced +-1 the long way round:
    bits = torch.randint(0, 2, shape, generator=gen, dtype=torch.int64)  # 8 B/elt
    n    = bits.to(torch.float32) * 2.0 - 1.0
    out.copy_(n.to(torch.bfloat16))
At d_total=917,504 that is an INT64 buffer of 7.34 MB per slot plus a 5-kernel
cast/scale/copy chain: ~42 MB of traffic and ~6 kernels per slot per token to
produce 1.83 MB of +-1. It also built a fresh torch.Generator per slot per token
and derived the blake2b seed on the host inside the decode loop. The same routine
was called once per token record during assembly (65,536 of them per step).

FIX  (verl/verl/trainer/es_token/noise_kernel.py)
------------------------------------------------
Draw +-1 DIRECTLY, in the destination dtype, one Triton launch for a batch of
rows, from Triton's counter-based Philox (tl.randint -> low bit -> +-1). No
generator state, no host RNG, no intermediate buffer. Supporting changes:
  - build_seed_table() derives every (token, slot) seed for a wave ONCE and
    uploads them, so the decode loop does no blake2b and no H2D copy;
  - assembly fills a whole chunk in ONE launch (was m x ~6 kernels per chunk).
A torch fallback is kept (non-Triton envs, sample_method != bernoulli); it still
avoids the int64 buffer via Tensor.random_(0, 2) straight into the destination.
The implementation is chosen once at import, so decode and assembly can never
disagree within a run.
